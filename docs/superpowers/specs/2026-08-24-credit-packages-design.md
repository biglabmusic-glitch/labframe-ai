# Пакеты генераций вместо подписки — дизайн

Дата: 2026-08-24
Статус: согласован, готов к плану реализации

## Проблема и цель

### Найденный баг: «в месяц» не существует

UI обещает «10 обычных генераций **в месяц**» и «Pro — 2 000 ₽/**мес**»
(`app/src/lib/plans.ts`, `0012_two_plans.sql`). В коде **нет ничего, что обнуляет
счётчики раз в месяц**: единственное место с `usage_used := 0` — триггер
`apply_plan_limits`, который срабатывает только при *смене плана*. Поле
`usage_period_start` пишется, но не читается никем. Из четырёх миграций с `pg_cron`
(`0002`, `0003`, `0014`, `0015`) все задачи обслуживают очередь job-ов, ни одна не
трогает лимиты.

Пока `LIMITS_DISABLED=1` (демо-период) этого не видно. Но при включении оплаты
в текущем виде подписчик заплатил бы второй месяц и **не получил бы новых
генераций**. Баг нашёлся до запуска продаж, а не после.

### Почему пакеты, а не починка подписки

1. **Автосписание самозанятому в ЮKassa включается только через менеджера** и может
   быть не согласовано. Разовый платёж подключается без согласований.
2. **Аудитория работает неравномерно.** У зубного техника бывает месяц с двадцатью
   работами и месяц с двумя. За подписку в пустой месяц он платит зря и отписывается;
   пакет не сгорает и обиды не вызывает.
3. **База уже работает как пакеты.** Реферальная награда (`bumpLimit()` в
   `_shared/referral.ts`) и админ-бонусы (`handleGrantCredits`) начисляются
   *прибавлением* к `usage_limit` — то есть баланс уже есть, он просто называется
   лимитом.

Цель: привести модель и названия в соответствие с тем, что код делает, и подготовить
почву для приёма денег.

## Согласованные решения

1. **Пакеты:** 20 / 50 / 150 генераций за 700 / 1500 / 3500 ₽ (35 / 30 / 23 ₽ за штуку).
2. **Бесплатный старт:** 5 генераций при регистрации.
3. **Премиум-генерации** (режим «Индивидуальность»): списываются **из того же баланса**,
   но по 3 штуки за генерацию. Отдельный premium-счётчик упраздняется.
4. **Ничего не сгорает и не обнуляется.** Срока действия у пакета нет.
5. **Приём денег на первом этапе — вручную** (см. ниже), без платёжной интеграции.

Себестоимость генерации ≈ 4 ₽ (Replicate + polza.ai), так что маржа на всех пакетах
кратная; цены выбраны по психологии, а не по себестоимости.

## Модель данных

Было: `usage_limit` (сколько всего можно) + `usage_used` (сколько потрачено),
баланс = разница. Плюс параллельная пара `premium_limit` / `premium_used`.

Стало: одно поле `credits` — остаток генераций.

| Событие | Действие |
|---|---|
| Регистрация | `credits = 5` (default колонки) |
| Покупка пакета | `credits += 20 / 50 / 150` |
| Обычная генерация `done` | `credits -= 1` |
| Генерация с декором `done` | `credits -= 3` |
| Реферальная награда | `credits += bonus` |
| Бонус из админки | `credits += N` |

**Списание — по факту `done`, а не при создании job-а.** Это сохраняет текущее
поведение (`bump_usage_on_done`): за упавшую генерацию пользователь не платит.
Проверка на входе (`create-job`) остаётся отдельно — она гейтит, а не списывает.

**Стоимость генерации — константа на бэке**, не приходит с фронта: иначе клиент мог бы
объявить декор-генерацию обычной. Резолвится из `decor_preset`, как уже делает
`bump_premium_on_done`.

## Миграция `0016_credit_packages.sql`

`users` — добавить:

- `credits int not null default 5` — остаток генераций.

Backfill существующих (боевые пользователи есть, 24 работы сделано):

```sql
update public.users set credits = case
  when is_admin     then 9999                      -- админы работают без лимита
  when plan = 'pro' then 50                        -- подарок: реально никто не платил
  else greatest(usage_limit - usage_used, 5)       -- остаток, но не меньше 5
end;
```

Триггеры:

- `bump_usage_on_done` — **заменить** на `spend_credits_on_done`: при переходе
  `jobs.status` в `done` списывать 1, а если `decor_preset is not null` — 3.
  Списание не уводит баланс ниже нуля (`greatest(credits - cost, 0)`).
- `bump_premium_on_done` (из `0011`) — **удалить**, premium-счётчика больше нет.
- `apply_plan_limits` — **удалить**. Планов больше нет, обнулять нечего;
  именно этот триггер был единственным местом «сброса» и источником путаницы.
- `enforce_usage_limit` — не возвращать (снят в `0005`), гейт живёт в `create-job`.

Старые колонки `usage_used`, `usage_limit`, `usage_period_start`, `premium_used`,
`premium_limit` **не дропаем в этой миграции** — оставляем на один релиз как страховку
отката, дропаем отдельной миграцией после проверки на проде. Enum `plan` тоже
остаётся: он в `users.plan` и в типах, снос — отдельная зачистка.

## Приём денег на первом этапе — счёт из кабинета ЮKassa

Сайта и автоматического эквайринга ещё нет; они в следующем заходе. Но продавать
можно сразу, законно и с автоматическими чеками:

```
«Купить 50 за 1500 ₽» → открывается чат с владельцем
        → владелец выставляет счёт в личном кабинете ЮKassa (ссылка/QR)
        → клиент платит по СБП
        → чек в ФНС уходит автоматически (НПД 4%)
        → начисление в админке (handleGrantCredits)
```

Кнопка открывает `https://t.me/{VITE_OWNER_TG}` через `WebApp.openTelegramLink()`
с префиллом текста («Хочу пакет 50 генераций за 1500 ₽»). Это не заглушка, а рабочая
схема: она проверяет главную гипотезу — готовы ли люди платить — **до** вложений
в сайт и интеграцию эквайринга.

### Почему именно так

- **ЮKassa работает с самозанятыми без ИП и расчётного счёта**, поддерживает СБП и
  позволяет выставлять счета ссылкой/QR **из личного кабинета, даже без сайта**.
  Чеки формируются автоматически, вручную в «Мой налог» бить не нужно.
- **Т-Банк не подходит на этом этапе.** Продукт «Самозанятость» для физлица — это
  карта плюс чеки; СБП там только как P2P-переводы на карту, платёжных ссылок нет.
  СБП-ссылки и API живут в «Т-Бизнесе», а он требует расчётный счёт, то есть ИП или
  ООО. Пересмотреть при переходе на ИП.
- **Ссылку присылает человек в личной переписке, а не мини-апп.** Правило Telegram
  требует продавать цифровые товары внутри Telegram только за Stars; кнопка в приложении
  ведёт в чат, а не на оплату. Автоматическая выдача платёжной ссылки внутри мини-аппа
  на этом шаге сознательно не делается — она появится на сайте, вне Telegram.

Ник владельца берём из `VITE_OWNER_TG` на Vercel, а не хардкодим: контакт для продаж
меняется чаще, чем код, и захардкоженный ник потребовал бы релиза. Если переменная
не задана — кнопка «Купить» скрывается, чтобы пользователь не упирался в битую ссылку.

Значение на момент написания: `VITE_OWNER_TG=DanyaSanta` (без `@`).

## Вне scope этого шага

- Сайт вне Telegram и **автоматический** приём платежей через ЮKassa (следующий заход).
  Ручное выставление счетов из кабинета ЮKassa к коду отношения не имеет и доступно сразу.
- Вебхук оплаты, который сам начисляет `credits` и зовёт `grantReferralReward()`.
- Telegram Stars.
- Переезд БД в РФ (152-ФЗ), уведомление РКН, оферта и политика конфиденциальности.
- Дроп старых колонок и enum `plan` — отдельной миграцией после проверки на проде.
- Срок годности пакетов, скидки, промокоды на пакеты.

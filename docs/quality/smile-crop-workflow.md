# Примерка через локальный кроп

Изменение от 07.11.2026 заменяет ручной выбор зубов на два режима и локальный
кроп. Качество ответа реального AI требует отдельной проверки. Основной
генератор постов, оплата, доступ к пилоту и механизм асинхронных задач
не менялись этим изменением.

## Пользовательский сценарий

1. Пользователь выбирает фронтальный портрет с открытой улыбкой.
2. Локальный MediaPipe Face Landmarker находит рот. SAM и ручной выбор FDI
   в этом сценарии не используются. При ошибке определения отправка запрещена;
   запасного пути с загрузкой полного портрета нет.
3. Пользователь выбирает тотальную реабилитацию всех видимых зубов или
   фронтальную от клыка до клыка включительно. Оба режима охватывают обе
   челюсти. Общие цвет, форма и прозрачность края остаются в настройках.
4. Перед отправкой показан точный фрагмент для AI. Контекст ограничен губами
   и небольшим окружением; дополнительные поля кадра заполнены чёрным.
5. В зашифрованную задачу загружаются только этот PNG и маска внутренней
   области губ. В новых режимах Polza и fal Nano Banana получают одно фото
   с семантическим промптом; Flux Fill сохраняет собственный вход маски.
6. Сервер восстанавливает пиксели вне маски. Браузер вклеивает результат
   в локальный нормализованный исходник, сохраняя пиксели вне области рта.

Фронтальный режим просит AI сохранять премоляры и моляры. Это ограничение
промпта: отдельной проверенной сегментации жевательных зубов здесь нет.
Автоопределение находит область рта, а не распознаёт каждый зуб.

## Хранение и совместимость

Исходник и геометрия хранятся только в IndexedDB текущего устройства для
восстановления после перезагрузки. Срок доступности — 24 часа; просроченные
записи физически удаляются при следующей операции с этим хранилищем.
Удаление примерки удаляет также локальную запись. При недоступной IndexedDB
работа продолжается в памяти с предупреждением. Если исходник утрачен,
возвращается явно обозначенный фрагмент без обещания полного портрета.
Кроп снижает объём переданных данных, но не гарантирует анонимность.

Новый клиент до загрузки проверяет `rehabilitationModes` в ответе `prepare`.
Старый сервер приводит к понятной ошибке обновления, а не незаметной обработке
только верхней челюсти. Новый сервер сохраняет старый контракт без режима.
Для выпуска сначала обновляется функция `smile-preview`, затем фронт.
Ключи провайдеров, миграции и платёжный обработчик менять не требуется.

## Проверки

```powershell
npm run build --prefix app
deno test --allow-env --allow-net=deno.land:443 --unstable-sloppy-imports scripts/test-smile-crop.ts scripts/test-smile-crop-contract.ts
deno test --no-check --unstable-sloppy-imports scripts/test-smile-local-source.ts
deno test --allow-env --allow-read --allow-net=deno.land:443 --unstable-sloppy-imports supabase/functions/_shared/smile-preview_test.ts supabase/functions/_shared/smile-fal_test.ts
deno test --allow-env --allow-read --allow-net=deno.land:443,esm.sh:443 supabase/functions/smile-preview/index_test.ts
```

Растровый контракт тестируется на синтетических пикселях, без локальных
игнорируемых фотографий, пациентов или платной генерации. Проверены обе
челюсти, серверное кадрирование, защищённые пиксели, восстановление исходника,
истечение срока, сбои хранилища и гонка сохранения с удалением.
`--no-check` для теста IndexedDB нужен из-за типов браузера/Vite; код приложения
отдельно проходит TypeScript при сборке.

До признания готовности выпуска нужны реальные браузерные проверки на телефоне:
портрет → точный кроп → смена фото → повтор определения → оба режима →
реальный ответ AI → сравнение → перезагрузка → удаление. Сетевой журнал должен
подтвердить, что полного портрета нет в запросах. Человек должен проверить
реализм и сохранность жевательных зубов во фронтальном режиме. Тесты вклейки
и успешный ответ провайдера сами по себе этого не доказывают.

# Долгое ожидание примерки после запуска

08.11.2026 пользователь сообщил о вращающемся индикаторе после «Создать
примерку». Метаданные Storage показали: оба зашифрованных файла загрузились
между 08:10:05 и 08:10:07 UTC, сервер запустил обработку в 08:10:09.
В manifest не было номера задачи провайдера или результата. Остановка
Edge isolate в 08:11:16 имела причину EarlyDrop и 425 мс CPU; превышение
памяти/CPU журналом не подтверждено. Точная причина отсутствия ответа
провайдера не установлена; повторный платный запрос не выполнялся.

Обнаружены два недостатка обработки ошибок:

- Polza ID сохранялся после получения изображения. Сбой его скачивания
  мог оставить уже принятую задачу без номера для восстановления.
- Любой HTTP-отказ провайдера, включая явный 4xx, считался неопределённой
  отправкой и оставлял пользователя ждать общий 12-минутный предел.

Номер задачи теперь сохраняется до скачивания результата. Временный сбой
после подтверждения оставляет задачу доступной для проверки по этому номеру.
Явный HTTP 4xx завершает попытку понятной ошибкой; сеть и 5xx остаются
неопределёнными и не вызывают повторную отправку. В технический журнал
попадают только категория, безопасный код и HTTP-статус, без ответа AI.

Status различает отправку, подтверждённую обработку и отсутствие подтверждения
по истечении ограниченного времени ожидания. В последнем случае клиент останавливает индикатор,
сохраняет ту же задачу и предлагает проверить её статус. Задачи со старым
manifest поддерживаются; уже потерянный ID этим изменением не восстанавливается.

Повторная проверка журнала после выпуска v8 установила `submission-unconfirmed
timeout` в 08:32:14 UTC: ответ с ID не успел прийти за прежние 60 секунд.
Окно фонового запроса и порог `confirmation_pending` согласованно увеличены
до 120 секунд, ниже минимального wall-clock лимита Supabase в 150 секунд.
Это даёт больше времени на получение исходного ответа, но не создаёт
новый запрос и не гарантирует доступность провайдера. Регрессия проверяет,
что на 75-й секунде сохраняется `submitting`, а после порога возвращается
`confirmation_pending` без второй генерации.

Проверки: библиотечные тесты подтверждения до сбойного скачивания и отказов
400/401/402/403/422/429/503; API-сценарии восстановления результата без второй
генерации, отказа 422 и неподтверждённой отправки. Браузер проверяет круговой
индикатор этапов и остановку ожидания с повторной проверкой той же задачи.
